## Confirmed Cross-Task Decisions

- Meaningful cross-cutting decisions must be recorded in their established canonical document before a handoff closes. For the active UI effort this includes visual hierarchy, Card/Hand/board presentation, Action Bar and Slot semantics, interaction behavior, accessibility, engine/UI contracts, and probe acceptance. Each record must distinguish confirmed decisions, open questions, assumptions awaiting validation, and superseded guidance, and include rationale, owner, affected areas, and follow-up work. This coordination file remains an index and evidence ledger rather than the detailed decision source.
- `EncounterEngine` is the sole rules authority; scenes render projections and submit actions. See [ADR 0009](../adr/0009-use-a-headless-rules-sdk.md).
- Probe support is outside the engine, and rules randomness is seeded. See [ADR 0010](../adr/0010-keep-probe-support-outside-the-encounter-engine.md) and [ADR 0012](../adr/0012-use-seeded-randomness-for-replayable-encounters.md).
- The portrait HUD's Bottom Interaction Zone is reserved for direct player input, not combat telemetry. Encounter Records are off-HUD. See [CONTEXT.md](../../CONTEXT.md) and [ADR 0006](../adr/0006-use-a-portrait-first-direct-manipulation-combat-hud.md).
- Aegis Guardian Whelp Clear and Slow Top Card cleanup are specified as isolated replay contracts. The live deck and shared rules remain unchanged until their engine and probe coverage land. See [the acceptance contracts](../content/aegis-guardian-acceptance-contracts.md).
- Interception, ally targeting, multi-Hero behavior, and Phase II are deferred; they require a dedicated shared rules contract and UI specification before implementation.
- Engineering Enablement is a cross-functional responsibility, not a permanent agent. Each item must name a bounded user, small owned contract, canonical document, focused validation, non-goals, and independent verifier. A dedicated task is considered only when this backlog becomes sustained, independently actionable, and repeatedly blocks gameplay work; task creation still requires user direction. See [the operating contract](../agents/engineering-enablement.md).
- PM-to-EM delivery begins only from a user-approved, fully specified `.scratch/product-backlog/issues/<NN>-<slug>.md` with `Status: ready-for-agent`, handed to the coordinator by path. The coordinator owns decomposition, sequencing, dependencies, and closure while preserving the confirmed product outcome; outcome changes route back to PM and the user. Implementation tracking lives in a separate `.scratch/<feature>/` directory. See [the issue-tracker workflow](../agents/issue-tracker.md).
- The Orchestrator is the authority hub for durable assignment, ownership, dependencies, verification, and closure, not a message bottleneck. Roles may collaborate directly on bounded domain questions; when direct work changes shared scope, ownership, dependencies, or user-approved intent, the canonical source is updated and the Orchestrator receives a concise routing notice. Product-outcome changes still route to PM and the user. See [the recovery-kit communication contract](../agents/recovery-kit.md).
- Test Automation owns deterministic probes and reproducible validation. Playtester is an on-demand, read-only role for independent hands-on evidence of eligible player-facing claims; it never implements, edits repository files, authors probes, or owns closure. The Orchestrator creates a separate local task only after the [Playtesting activation gate](../agents/playtesting.md#activation-gate) passes and archives it after verified closure.
