# Author Heroes as first-class content in data/heroes/

A Hero is one authored JSON definition under `data/heroes/` — identity, `max_health`, and the `signature_card` printed on them — and an Encounter fields a Hero by id through its `hero` field, with `fields_signature: false` available to hold the printed card back (the teaching slice uses it). This replaces the inline trio the Encounter carried (`primary_hero_id`, `primary_hero_title`, `player_health`) and moves `signature_card` off the Encounter onto the Hero, which is where D-064 always said it was printed — the catalog comment even marked the arrangement as temporary, "while Heroes live inline on Encounters".

Inline Heroes were fine while one Hero existed in two Encounters that were the same fight twice. They stop being fine at exactly the moment the design team is asked to create characters: an inline Hero cannot exist before an Encounter does, cannot be shared by two fights without hand-kept copies (the Ashen Trial and the teaching slice already restated Elian's 34 health twice, with nothing checking agreement), and gives the character design bible's contract no authored artifact to land on. The Hero definition is now reachable Encounter content, so a retuned health pool or Signature starts a new evidence cohort for every fight that fields the Hero — the same rule a retuned card already follows.

What stays on the Encounter is everything the fight decides rather than the character: start hexes, the deck list, `slot_count`, `hand_refill_target`. The deck stays per-Encounter deliberately — evaluation decks exist to vary it against one fight, and a Hero-owned deck would put the promotion the measurement gates back into the definition. A Hero still carries no Role field: the deck's unanimous Role Keyword states it, and `heroRole` reads it back out. The Boss's identity fields stay inline on the Encounter — a Boss's substance already lives in its Programs, and nothing yet needs one Boss in two arenas; if that day comes, this ADR is the pattern to repeat, not a precedent that it happened for free.

Scenario compatibility pinned one choice: Elian's id stays `guardian`, because committed Scenarios address him by `sourceId` and an id is stable by contract — it never changes because a display name would read better.

## Amendment, 2026-08-21: the id is `elian`

That id was renamed to `elian`, and the reason is not that a display name reads better — it is that `guardian` was never this Hero's name. It was the Role they play, written into the one field the game addresses a person by, at a time when one Hero existed and the two were indistinguishable. A second tank makes the collision concrete: Kessa Varn guards the party too, and an id that names that job cannot be hers as well. Every party-facing surface reads the id's owner as a person — a Scenario step, a Beat's target, the seat a console hands control to — so the Hero the party calls Elian is `elian`.

The stability contract is unchanged, and this rename is what paying it looks like rather than an exception to it: nothing in `data/`, the engine, the UI, or the tooling addresses the old id any more. The decision-log rows and resolved issue records that mention `guardian` keep it, because they are accounts of what happened and history is left as written. The three committed Scenarios were rewritten in the same commit (`sourceId` and `targetId` alike), and `brand_trial_duo_line` still replays to the same asserted line, because a Scenario is a sequence of actions and renaming who takes them is not a different sequence. The next id that stops fitting gets the same treatment or none: a rename that leaves one stale reference behind is the thing the contract refuses.

The same pass separated the two names a Hero has. `title` is now the first name — `Elian`, `Maren` — because it is the string every readout prints, and `full_name` carries `Captain Elian Voss` as flavour the Hero Frame's hold tells.
