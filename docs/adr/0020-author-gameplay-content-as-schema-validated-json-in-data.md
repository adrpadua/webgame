# Author gameplay content as schema-validated JSON in data/

Gameplay content — cards, keywords, boss programs, encounters, hazards, minions, charge modifiers — is authored as JSON files under `data/`, the directory reserved for machine-readable payloads since its README was written. Zod schemas living inside the Encounter Engine validate every file at load and are the single definition of each content shape; TypeScript types are inferred from those schemas rather than written by hand. This replaces the de facto `.tres` format, which no ADR ever ratified: the existing 39 resource files (14 cards, 3 Embermaw boss programs, 1 encounter, 10 keywords, and singletons) are ported by hand once, and the `.tres` files freeze with the Godot codebase (ADR 0019) as reference copies. The same pattern extends to evaluation decks and to Scenarios (ADR 0019), which also live as JSON under `data/` and validate through the same load pass; the legacy boss-action resources and the content-catalog singleton are not ported, because the Boss Program model and the `data/` directory itself replace them structurally.

JSON over TypeScript modules keeps content client-neutral — the frozen Godot build or any future client can parse it without a TS toolchain — and keeps authoring diffable and schema-checked, which matters for a workflow where agents write and review content. The schema-at-load pass takes over the job `ContentValidator.gd` did for `.tres` resources, but as a compile-adjacent contract instead of a separate 290-line validator. A `.tres`-to-JSON converter was rejected because the corpus is one afternoon of hand porting and a converter would both cost more than the content and keep `.tres` alive as an authoring format on a frozen engine. Content identity fingerprinting from the Encounter Record contract (SHA-256 over stable IDs) carries forward over the JSON payloads in `schema_version: 2` records.
